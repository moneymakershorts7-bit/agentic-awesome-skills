# 运行后反思流程 (Post-Run Reflection)

## 概述

**每次运行 sec-userspace 后（包括扫描、测试、功能验证），必须执行本文档的反思流程。**

反思分两个阶段：
1. **告警验证反思** — 逐条验证告警真实性，过滤误报
2. **功能一致性反思** — 对照 SKILL.md 验证功能承诺与实际是否一致

两个阶段都完成后，才能向用户输出最终结果。

---

## 阶段一：告警验证反思

### 核心原则

> **准确性 > 告警数量**。宁可漏报一条低置信度告警，也绝不能向用户报告大量误报。
> **验证优先于汇报**。没有用工具验证过的告警，禁止标记为"需要关注"报给用户。

### 禁止行为（NEVER）

- **禁止"建议用户检查"** — 必须自己执行命令验证并给出确定结论
- **禁止凭经验分类** — "可能是误报"不可接受，必须有验证命令输出或 lessons-learned 记录作为依据
- **禁止先报告后验证** — 必须验证完所有告警后，才输出最终报告
- **禁止猜测告警有效性** — "建议确认"、"应该是安全的"等措辞说明你没有验证

### Step 0: 查阅历史误报案例（MANDATORY - 必须首先执行）

**在开始逐条验证之前，必须先读取 [references/lessons-learned.md](references/lessons-learned.md)**。

已记录的误报模式可以直接判定，无需重复执行验证命令：
- 匹配模块名 + 环境 + 告警内容 → 直接标记为已知误报
- 仅当告警不在 lessons-learned 中时，才需要执行工具命令验证

这一步能大幅减少重复验证工作，提高效率。

### Step 1: 环境识别

先判断服务器角色，这影响误报判断：

```bash
# 检查是否为 WSL2 环境（影响内核、进程、内存告警判断）
uname -r | grep -q microsoft && echo "WSL2"

# 检查是否为 K8s 节点
ps aux | grep -E 'kubelet|kube-apiserver|etcd' | grep -v grep

# 检查是否为开发机（AI Agent 运行环境）
ls -la /home/*/.vscode-server /home/*/.qoder-server 2>/dev/null
ps aux | grep -E 'qodercli|node.*qoder|node.*vscode' | grep -v grep

# 检查是否为容器环境
cat /proc/1/cgroup 2>/dev/null | grep -q docker && echo "Docker"
docker ps 2>/dev/null || crictl ps 2>/dev/null
```

**环境识别结果直接影响后续判断**：
- **WSL2 开发机**: 内核告警、进程孤儿、RWX 内存均为 WSL2+Node.js 正常特征
- **AI Agent 运行环境**: Qoder/IDE 进程的内存、网络、权限告警均为正常运行行为
- **K8s 节点**: 挂载、网络策略、容器进程告警需要按 K8s 语境判断

### Step 2: 逐条工具验证

**每条告警必须执行对应的验证命令，将命令输出作为判定依据：**

| 告警类型 | 必须执行的验证命令 | 判定标准 |
|----------|-------------------|----------|
| **凭据泄露 (.env)** | `git check-ignore <file>` + `git ls-files --error-unmatch <file>` | git 已忽略且未追踪 → 误报 |
| **Dockerfile ENV 凭据** | `grep -n 'ENV.*KEY\|ENV.*TOKEN\|ENV.*SECRET' <Dockerfile>` | grep 无匹配 → 误报；有匹配 → 检查是否为占位符 |
| **sudo NOPASSWD** | `sudo cat /etc/sudoers.d/*` + 检查用户记忆 | 已知配置 → 标记为已知，非入侵 |
| **AI Agent 进程告警** | `ps aux \| grep <PID>` 确认进程归属 | 属于 Qoder/Node.js/IDE → 误报 |
| **内核完整性** | `uname -r` 检查是否 WSL2/容器内核 | microsoft-standard-WSL2 → WSL2 特征，非真实威胁 |
| **端口扫描/横向移动** | `ps aux \| grep <PID>` 确认触发进程 | sec-userspace 自身触发 → 自检测误报 |
| **孤儿进程** | `ps -p <PID> -o ppid,cmd` 确认进程链 | 系统守护进程/IDE 进程 → WSL2 正常行为 |
| **NPM Typosquatting** | `npm view <package> 2>/dev/null` 或检查包来源路径 | 属于知名 IDE 扩展目录 → 误报 |
| **Prompt 注入/隐写** | 检查触发源文件内容 | AI 开发工具正常 prompt → 误报 |
| **PATH 修改** | `cat <file> \| grep PATH` 确认修改内容 | 标准开发工具路径添加 → 正常配置 |
| **Webshell 时间戳** | `rpm -qf <file>` 或 `dpkg -S <file>` 或 `ls -la <file>` 确认来源 | 属于系统包管理器安装 → 误报 |
| **Suspicious Process** | `ls -la /proc/{pid}/exe`, `dpkg -S {binary}` | 属于合法包 → 误报 |
| **Network Anomaly** | `ss -tnp`, `dig {domain}` | 已知合法服务 → 误报 |
| **Credential leak (regex)** | 提取变量上下文，检查变量名+值格式 | 变量名为 DISTRO_COMMIT/PID 等 → 误报 |

### Step 2.1: credential_analyzer 误报过滤规则

credential_analyzer 的某些正则模式过于宽泛，必须执行上下文验证：

| 宽泛模式 | 误报案例 | 验证方法 |
|----------|----------|----------|
| Together AI API Key | Git commit hash、SHA256 哈希 | 必须拒绝仅凭长度匹配的告警 |
| Azure Client/Application ID | 连接令牌、随机 ID | UUID 不等于 Azure 凭据 |

**上下文验证流程**：
1. 提取匹配内容，检查变量上下文
2. 真实凭据：变量名含 `API_KEY`、`SECRET`、`PASSWORD`、`TOKEN` 且值符合服务特定格式
3. 误报：变量名为 `DISTRO_COMMIT`、`SERVER_TOKENFILE`、`PID`、`SESSION_ID`
4. 仅当变量名和值都符合特定云服务凭据特征时，才认定为有效告警

### Step 3: 汇总判定并输出

验证完所有告警后，按以下格式输出：

```markdown
## 安全扫描结果

### 环境识别
- **服务器角色**: WSL2 开发机 / K8s Master / 生产服务器
- **AI Agent**: Qoder 运行中 / 无
- **验证命令**: `uname -r` → `6.6.87.2-microsoft-standard-WSL2`

### 扫描结论
- **结论**: 系统安全 / 存在风险 / 高度可疑 / 已被入侵
- **总告警数**: X 条 → **已验证有效**: Y 条, **已验证误报**: Z 条

### 已验证有效告警 (需要处理)
| 告警 | 验证命令 | 验证结果 | 修复建议 |
|------|----------|----------|----------|
| 具体告警标题 | 执行的验证命令 | 命令输出摘要 | 修复命令 |

### 已验证误报 (已过滤)
| 类别 | 数量 | 验证依据 |
|------|------|----------|
| AI Agent 进程告警 | N 条 | ps 确认为 Qoder node 进程 |
| WSL2 内核告警 | N 条 | uname -r 确认为 WSL2 虚拟内核 |
```

## 阶段二：功能一致性反思

### 反思时机

**必须执行反思的场景**:
1. 运行 sec-userspace 扫描后 (quick/full scan)
2. 单元测试通过后
3. 功能测试完成后
4. Mock 测试通过后
5. 真实环境扫描验证后

### 反思执行流程

**第一步: 对照 SKILL.md 功能清单**

```bash
# 读取 SKILL.md，提取功能承诺清单
# - 支持的扫描模式 (quick/full)
# - 承诺的检测能力 (分析器数量、ATT&CK 覆盖)
# - 承诺的输出格式 (报告类型、语言)
# - 承诺的性能指标 (扫描时长、内存占用)
# - 承诺的误报处理机制
```

**第二步: 验证测试结果与功能承诺的一致性**

| 验证维度 | 检查项 | 验证方法 |
|----------|--------|----------|
| **功能完整性** | SKILL.md 承诺的检测项是否都执行了? | 对比报告中执行的 analyzer 列表与 SKILL.md 描述 |
| **输出格式** | 报告格式是否与 SKILL.md 描述一致? | 检查输出文件 (md/json/html) 是否齐全 |
| **性能指标** | 扫描时长是否符合 SKILL.md 承诺? | quick < 90s, full < 10min |
| **误报处理** | 是否有 SKILL.md 承诺的误报过滤机制? | 检查白名单、上下文验证是否生效 |
| **用户体验** | 用户操作流程是否与 SKILL.md 描述一致? | 按 SKILL.md 步骤操作，验证是否顺畅 |

**第三步: 记录不一致项并立即修复**

```markdown
## 测试反思报告

### 测试场景
{例如: 执行 quick scan 验证系统安全性}

### SKILL.md 功能承诺
1. {承诺1}
2. {承诺2}

### 测试实际结果
1. {结果1}
2. {结果2}

### 不一致项分析

| 不一致项 | 严重程度 | 原因分析 | 修复方案 |
|----------|----------|----------|----------|
| {不一致项} | P1/P2 | {原因} | {方案} |

### 修复计划
**立即执行** (阻塞 Release):
- [ ] {修复项}

**后续优化** (不阻塞当前任务):
- [ ] {优化项}

### 反思结论
- 功能一致性: {百分比}% ({一致项}/{总承诺项})
- 需要修复: {不一致项数量} 项
- 测试通过率: {通过项}/{总测试项}
```

**第四步: 立即执行修复**

- 发现**功能承诺未实现** → **立即开发**，不要留到以后
- 发现**误报/漏报问题** → **立即优化**，准确性是核心指标
- 发现**性能不达标** → **立即优化**，性能是第一优先级
- 发现**SKILL.md 描述过时** → **立即更新文档**，保持文档与代码同步

### 反思检查清单

每次反思必须确认以下检查项:

**功能一致性**:
- [ ] SKILL.md 承诺的所有扫描模式都已实现
- [ ] SKILL.md 承诺的所有检测能力都已实现
- [ ] SKILL.md 承诺的输出格式都已实现
- [ ] SKILL.md 承诺的性能指标都已达标
- [ ] SKILL.md 描述的用户操作流程与实际一致

**准确性验证**:
- [ ] 误报率在可接受范围内 (< 20%)
- [ ] 无已知漏报场景
- [ ] 白名单机制正常工作
- [ ] 上下文验证生效

**用户体验**:
- [ ] 报告易于理解 (中文报告完整)
- [ ] 修复建议可操作
- [ ] 错误提示清晰
- [ ] 扫描进度可见

## 反思示例

```markdown
## 测试反思报告

### 测试场景
执行 full scan 验证系统安全性，扫描目标: WSL2 开发环境

### SKILL.md 功能承诺
1. 支持 quick (< 90s) 和 full (< 10min) 两种扫描模式
2. 107+ 分析器，120+ ATT&CK 覆盖
3. 自动生成中文报告 (sec-report-cn.md)
4. 误报率 < 20%，支持白名单过滤
5. 提供修复建议和修复命令

### 测试实际结果
1. full scan 执行成功，耗时 12.6s (优于承诺)
2. 190个分析器，189个执行成功，37个安全类别完全覆盖
3. 报告包含中文版 (sec-report-2026-04-22-cn.md, 38KB)
4. 16个告警中约 12个是误报，误报率 75% (远超 20% 承诺)
5. 所有告警都提供了修复建议和命令

### 不一致项分析

| 不一致项 | 严重程度 | 原因分析 | 修复方案 |
|----------|----------|----------|----------|
| 误报率 75% 远超承诺 | P1 | WSL2 内核差异未适配，Agent 进程被误判 | 添加 WSL2 环境识别，增加 Agent 进程白名单 |
| Kernel 检测全部误报 | P1 | 标准 Linux 检测逻辑不适配 WSL2 | 添加 WSL2 内核检测跳过规则 |

### 反思结论
- 功能一致性: 80% (4/5 项承诺一致)
- 需要修复: 2 项 (全部与误报相关)
- 测试通过率: 100% (所有分析器执行成功)
```

## 禁止行为

- 测试通过后直接提交，不验证功能承诺
- 发现不一致项但说"以后再说"
- 仅关注测试通过，不关注功能完整性
- 忽略 SKILL.md 与代码的差异
- 不记录反思结果，下次重复同样的问题

## 必须行为

- 每次运行后立即进行反思（两个阶段都不可跳过）
- **验证前先读 [lessons-learned.md](lessons-learned.md)**，已记录的误报可直接判定
- **验证后发现新误报，必须追加到 [lessons-learned.md](lessons-learned.md)**
- 发现不一致项立即修复
- 将反思结果同步到 todo/ 或文档
- 定期回顾 SKILL.md 确保与代码同步

## 附录：快速验证参考表

> 来源：原 verification-workflow.md，精简为表格形式供快速参考。

**时间约束**：验证过程不应超过 10 分钟。

### 告警验证方法速查

| 告警类型 | 验证方法 | 误报判定标准 |
|----------|----------|-------------|
| 可疑进程 | `ls -la /proc/{pid}/exe`, `dpkg -S {binary}` 或 `rpm -qf {binary}` | 属于合法软件包 |
| 网络异常 | `ss -tnp`, `dig {domain}`，检查是否为云服务/CDN | 已知合法服务 |
| 可疑文件 | `stat {file}`, `file {file}`, `dpkg -S {file}` | 系统/开发工具产物 |
| Shell 历史 | 查看上下文（前后 5 行） | 正常运维操作 |
| 凭证泄露 | 检查是否为占位符/示例值 | 模板/示例占位符 |
| SSH 配置风险 | 与安全基线对比 | 有补偿控制的有意配置 |
| 持久化 | 检查 crontab/systemd 脚本内容 | 已知合法软件任务 |
| Rootkit 迹象 | 验证内核模块签名，检查是否为内核线程 | 内核线程或合法模块 |

### 验证原则

- 每条告警需给出明确结论：**确认威胁** 或 **误报（附原因）**
- 无法验证的告警保留原始严重级别
- 发现新的可疑迹象应予以标记

### 排除误报后结论判定

| 剩余告警情况 | 最终结论 |
|-------------|----------|
| 存在 CRITICAL 告警 | **Compromised** - 立即报告并提供修复建议 |
| 存在 HIGH 告警 | **Highly Suspicious** - 建议调查 |
| 仅剩 MEDIUM/LOW | **At Risk** - 记录安全配置问题 |
| 全部为误报 | **No Intrusion** - 报告系统安全 |

### 报告展示规则

- 默认：仅展示 CRITICAL 和 HIGH 告警
- MEDIUM/LOW/INFO 默认隐藏（仅显示数量）
- 用户要求时展示完整列表
- 不可跳过验证步骤；CRITICAL 告警必须逐条验证
- 验证命令仅限只读操作
